# 管理者の運用と検証

[開発版の案内](../README.md) · コマンドの実行場所は `hermes-ai-hub/` です。

## 管理者のログインと権限

[AI Hub](http://127.0.0.1:18733) に個人の管理者IDでログインすると、自分のワークスペースが開きます。管理操作・閲覧専用のどちらのアカウントも、営業企画部の合成資料（A社）で依頼を作成できます。仕事履歴と Hermes の実行環境はアカウントごとに独立しています。左サイドバーの「管理者メニュー」→「管理者画面」で管理ページを開き、「AI Hub に戻る」でワークスペースへ戻れます。管理者用URLへの初回の直接アクセスは、ループバック限定の HTTP Basic に対応しています。

社員画面・管理画面の左下にあるアカウントアイコンからログアウトすると、アカウント選択画面が開きます。ローカル検証用の社員は氏名を選んで切り替えます。管理者として入り直すには、個人の管理者IDとパスワードを入力してください。

初期設定ではローカル検証用に青木（`aoki`）と森（`mori`）を作成します。各自のパスワードは `.runtime/admin-accounts/<ID>` に保存されます。Macで青木のパスワードをコピーする例は `pbcopy < .runtime/admin-accounts/aoki` です。二人の操作を同時に確認する場合はブラウザのプロファイルを分けてください。

別の担当者を追加するには、プロジェクトのディレクトリで `node infra/init.mjs <個人ID>` を実行し、起動手順の Compose コマンドで本人用の Hermes と Hub を起動します。初回から個人IDを引数で指定することもできます。既存のパスワードは再発行されません。以前の共有アカウントから移行する場合は、[開発版の起動手順](../README.md#起動と操作)を再実行すると、Composeが個人用の認証ファイルをマウントします。

### ローカルのEntraグループ同期

検証用のJSONに `tenant`、`bindings`（各社員の `actor` と `objectId`）、`groups`（グループの `id`、`name`、許可する `models`）を指定します。IDには合成のUUIDを使います。形式の例は [SCIM・モデル選択のブラウザ試験](../test/scim-model-selection-browser.mjs) にあります。

専用のComposeプロジェクトに次のような上書き設定を加えます。`グループと権限 → Entra ID 同期` で、検証用の配信を確認し、対応するAI Hubグループと受信メンバーを選びます。

```yaml
services:
  hub:
    environment:
      AI_HUB_LOCAL_DIRECTORY_FILE: /run/local-directory.json
    volumes:
      - ./.runtime/local-directory.json:/run/local-directory.json:ro
```

| アカウント | 権限 | 利用できる操作 |
|---|---|---|
| 青木（`aoki`） | 管理操作（`manager`） | 社員の所属変更・利用停止・再有効化、既存のモデル設定・手順公開、履歴の確認 |
| 森（`mori`） | 閲覧専用（`auditor`） | 社員管理とモデル設定の変更履歴、停止した依頼のHermes送信記録、モデル利用記録の閲覧 |

権限はHubの起動時にホストの `.runtime/admin-accounts/.roles.json` から読み込みます。既存環境では `node infra/init.mjs` で初期設定を作成してHubを再起動します。以降の設定変更はこのファイルで個人IDに `manager` または `auditor` を割り当て、Hubを再起動して反映します。個別の割り当てがないアカウントは閲覧専用です。

森は「管理操作の監査ログ」で田中を選び、青木の停止履歴にある「停止した依頼の送信記録」から理由、再有効化の日時、依頼別の追加試行件数、Hermes受付IDを確認できます。[閲覧権限での動作確認](../evidence/admin-roles.md)

## 会社標準の手順を編集する

管理者は「手順の公開」→「会社標準の手順」で5件すべてを編集できます。手順名、用意するもの、受け取れるもの、依頼例、Hermesが使う手順本文を変更し、変更理由を入力して「新版を公開する」を押します。公開した版は新しい依頼に適用されます。受付済みの依頼は受付時の版を参照します。「更新商談の準備」は営業企画部、ほかの4件は全社員に配布します。改訂の操作者、版、理由は監査ログで確認できます。

## 管理者による標準モデルの公開

「モデル設定」の「接続方式から登録」では、直接 API、Cloudflare AI Gateway、AWS Bedrock、OpenAI 互換 API の接続設定を下書きに保存できます。設定の確認では入力形式と接続先を表示します。公開できるモデルの登録と接続テストは、運用者が用意した接続先をモデル台帳で選んで行います。

1. **モデルを登録**で表示名・接続先・モデルID・データ区分を指定します。ローカル A は `fixture-model`、ローカル B は `fixture-model-b` を提供します。登録済みならその行から操作します。
2. **接続テスト**で合成の商談資料を使い、質問と回答反映後のメモを検証します。結果欄には出力、接続テストの所要時間、提供元が返した使用量が表示されます。
3. **公開内容を確認 → 全社員に公開する**で、表示中の設定版を条件に新しい版を一括公開します。同時に別の管理者が先に公開した場合は、更新された設定を確認してやり直せます。

社員の各依頼は受付時の設定版を持ちます。質問と回答後のメモは同じ設定版で生成し、依頼詳細でモデルと版を確認できます。旧データは v1（合成モデル A）に移行します。社員コンテナの接続先はAI Hubの内部モデル接続口に固定し、依頼を受け付けた版から送信先を解決します。モデルAとBは別の合成サービスとして起動し、実際に受けた依頼ID・段階・設定版を各サービスのログに残します。

この構成の接続先と資格情報はサーバー側で運用管理し、管理画面では登録済み接続先を選びます。接続テストは合成案件を各モデルへ送り、日付・出典番号・指定した回答の引用を確認します。各記述と出典の対応は別途原文と照合します。

## 社員の所属変更

「ユーザアカウント」の社員詳細には、本人用コンテナのIDと定期実行が表示されます。管理操作の権限があるアカウントは、同じ社員の予約を作成・編集できます。新しい予約は一時停止で登録でき、実行を有効にすると日本時間で計算した次の予定枠から処理します。

各社員の既定コンテナは従来の Runs API 設定を使います。運用者は必要に応じて、`AI_HUB_RUNTIME_ALIASES` に社員別の追加接続を JSON で指定できます。

```json
{"sato":[{"id":"sato-secondary","url":"http://sato-secondary:8642","key_ref":"SATO_SECONDARY_KEY"}]}
```

API キーの値は Hub プロセスの環境変数に設定します。受付記録の照合に別の接続先がある場合は、同じエントリの `receipts` に指定します。各IDは社員と接続先の組み合わせに割り当て、切替後も未照合の実行が残る接続先はそのIDで維持します。管理画面での切替は次の送信から適用され、受付済みの実行は受付時のIDを使って追跡します。

管理画面の「社員の所属・利用状態」から対象者の「所属を変更」を開き、異動先の部門名を入力して確定します。公開手順は公開先の部門名と社員の現在の所属が一致するときに利用できます。所属は Hub の SQLite に保存されます。

確認待ちで異動した社員は、以前の画面からも回答を保存できます。回答後の依頼には「所属変更により停止」と表示され、Hermes へのメモ作成依頼は発生しません。異動で停止した依頼は、元の部門に戻っても自動再開しません。同じ部門に残る社員は通常どおり利用できます。

[管理画面のユーザアカウント](http://127.0.0.1:18733/admin.html#memberships) ／ [田中・佐藤の動作検証](../evidence/employee-membership.md)

## 社員の利用停止と再有効化

管理画面の「社員の所属・利用状態」で、対象社員の「利用を停止」を選んで確定します。停止中はワークスペースの閲覧、新規依頼、以前の画面からの回答を拒否します。回答は保存されません。確認待ち・受付済み・作業中・モデル停止で保留中の依頼は、この社員について「社員の利用停止により終了」になります。

「再有効化」を確定すると、社員は現在の所属で公開されている手順から新しい依頼を作成できます。利用停止で終了した依頼は履歴に残ります。続きの作業が必要な場合は、新しく依頼してください。

[停止中の回答、再有効化後の新規依頼、佐藤の継続利用の検証記録](../evidence/employee-access.md)

## 管理操作の監査ログ

社員の変更と、認証済み管理者が権限不足で拒否された操作を同じ時系列に表示します。「変更済み」には変更前後の値と理由、「拒否」には操作の対象・内容、操作者、日時、拒否理由を表示します。拒否の記録はこの機能の導入時から蓄積されます。対象社員・操作者のアカウントID・操作結果・期間を組み合わせて絞り込めます。期間は日本時間で開始秒と終了秒を含み、片側だけの指定もできます。「過去の記録を表示」でも条件が維持されます。

「CSV出力」で、表示時点の条件に一致する全件を新しい順に保存できます。未表示の過去ページも含みます。ファイルは日本語の列名を持つUTF-8（BOM付き）です。数式として解釈され得る先頭文字には、表計算ソフト用にアポストロフィを付けます。[CSVと画面の照合結果](../evidence/audit-csv.md) ／ [条件を切り替えた検証](../evidence/audit-filters.md) ／ [田中のB社依頼での検証](../evidence/admin-denials.md)

「管理操作の監査ログ」内の「CSV出力履歴」を開くと、出力者のアカウント、日時（日本時間）、対象社員、抽出した操作の操作者・結果・期間、出力件数を確認できます。出力履歴内の「出力者」「出力対象の社員」「出力種別」「出力日時の開始・終了」で絞り込めます。期間はCSVを出力し始めた日本時間で、開始秒・終了秒の両方を含みます。社員を選ぶと、その社員を指定して出力した履歴が表示されます。件数はヘッダーを除くデータ行数です。Hubが送信を完了した時点で確定し、途中で切断された出力は「送信完了未確認」と表示します。監査ログ本体のCSVには出力履歴が入りません。[出力者・社員・日時で絞り込んだ画面](../evidence/csv-export-history-filters/mori-tanaka.png) ／ [同じ出力期間の全履歴](../evidence/csv-export-history-filters/period.png) ／ [青木の確認画面](../evidence/csv-export-history/aoki.png) ／ [田中のB社依頼での照合記録](../evidence/csv-export-history/records.json)

「出力種別」で「監査ログのCSV出力」か「出力履歴のCSV保存」を選ぶと、該当する操作だけが表示されます。種別はCSV保存にも引き継がれ、保存時の条件を「抽出した履歴の種別」で確認できます。[青木が森の履歴2件を保存した記録だけを表示した画面](../evidence/history-source-aoki.png) ／ [保存した1行のCSV](../evidence/csv-export-history-aoki-history.csv) ／ [田中のB社依頼での照合記録](../evidence/history-source-verification.json)

出力履歴そのものを保存するには、「CSV出力履歴」で条件を選び「出力履歴をCSV保存」を押します。表示時点の条件に合う全ページを新しい順に保存します。出力者と抽出した操作の操作者は別の列で、出力件数は元のCSVのデータ行数です。この保存操作も「出力履歴のCSV保存」として記録され、更新後の一覧で確認できます。[青木が保存した田中の履歴CSV](../evidence/csv-export-history-mori-tanaka.csv) ／ [保存時の画面](../evidence/history-csv-aoki.png)

送信が完了した「出力履歴のCSV保存」には「保存した元の履歴を見る」があります。開くと、そのCSVに入った履歴を保存時の順序で確認できます。後から同じ条件で出力しても内容は固定されます。導入前の保存記録も元の履歴をたどれますが、各履歴の出力件数には現在の値を表示します。[青木が開いた元の2件](../evidence/aoki-saved-originals.png) ／ [同条件で再出力した前後の照合結果](../evidence/saved-originals-verification.json)

「保存した元の履歴を見る」で開いた監査ログのCSV出力には「元の監査ログを見る」があります。展開すると、そのCSVに含まれた操作の日時、対象、操作者、結果、理由を確認できます。出力後に同じ条件の操作が増えても、表示されるのは元の行だけです。[青木の画面で森のCSVから元の監査ログを開いた例](../evidence/saved-audit-originals.png) ／ [後続操作との照合結果](../evidence/saved-audit-originals.json)

保存記録から元の監査ログを開き、「利用停止（変更済み）」の「停止した依頼の送信記録」を押すと、その停止で終了した依頼のHermes受付IDと追加試行数を確認できます。送信記録の上部に、たどった保存記録と監査ログCSVの番号・出力者が表示されます。[青木の送信記録画面](../evidence/saved-dispatch-trace.png) ／ [同じ社員の別のB社依頼との照合](../evidence/saved-dispatch-trace.json)

所属変更・利用停止・再有効化を確定する際は、変更理由を入力します。管理画面の「管理操作の監査ログ」で社員を選ぶと、変更前後の値、日時（日本時間）、認証済みの管理者アカウント、理由を新しい順に確認できます。履歴の記録はこの機能の導入時から始まります。今回の個人認証への切替前に記録された `admin` は、当時の共有アカウントを表します。個人認証への切替後は、認証した個人IDを記録します。

利用停止の履歴にある「停止した依頼の送信記録」を開くと、その変更で停止した依頼ごとに、停止時のHubの送信試行数と現在までの追加試行数、送信日時・段階・Hermes受付IDが表示されます。受付結果が不明な試行は「受付未確認」と表示します。同じ画面で対応する再有効化の日時と理由を確認でき、依頼IDで絞り込んだモデル利用記録も開けます。

[管理画面の管理操作の監査ログ](http://127.0.0.1:18733/admin.html#employee-history) ／ [田中のB社依頼での照合結果](../evidence/employee-change-history.md) ／ [別々の管理者による停止・再有効化の検証](../evidence/personal-admin.md)

## 緊急停止と復元

- 管理画面の対象モデルで **緊急停止** を選び、理由を入力して確定します。そのモデルを使う新規依頼と接続テストを止め、各モデル呼び出しの直前にも停止状態を確認します。停止確定より前に送信を開始した処理は完了する場合があります。
- 確認待ちの依頼には回答できます。停止中なら回答を依頼に保存し、メモ作成を未送信のまま保留します。**停止を解除**しても保留中の依頼は自動送信されません。社員が依頼詳細で状態を更新し、**この依頼を再開**すると受付時の版で続行します。すでにHermesを起動した段階で停止を検出した依頼は、結果照合のため個別再開の対象から外します。
- **直前の標準設定に戻す**は、ひとつ前の公開版のモデルを新しい設定版として公開します。復元先のモデルが停止中なら操作を拒否します。各モデルの停止状態は**停止を解除**で個別に変更します。
- **モデル設定の変更履歴**では管理者・日時・理由・設定版を確認できます。移行前の公開履歴には当時の版とモデルを表示し、未記録の担当者・理由を補完しません。
- **モデル利用記録**は依頼IDで絞り込めます。1行は1回のモデル呼び出しまたは送信前の拒否を表します。詳細で照合ID、提供元が返した実モデル、HTTP結果、経過時間、使用量を確認できます。合成モデルのログに同じ照合IDが残ります。通信中断・結果不明・使用量欠落を区別し、会話本文や秘密値は利用記録に保存しません。

ブラウザ検証は [test/emergency-browser.mjs](../test/emergency-browser.mjs) で実行できます。稼働中のローカル合成環境と、現在・直前とも利用可能な別々のモデルを使います。標準モデルを実際に停止し、直前のモデルへ復元した状態を残します。Docker context は `AI_HUB_DOCKER_CONTEXT`、Playwrightの場所は `PLAYWRIGHT_PACKAGE` で指定できます。
