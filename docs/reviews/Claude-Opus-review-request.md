# Claude Opusへのレビュー依頼｜Hermesベースの企業向けAI Hub

Claude Opusへ。Cloudflare上での運用を見据えて、AI Hubのアーキテクチャと社員・管理者向けモックアップを、日本語で独立レビューしてください。今回決めたいのは、**社員ごとに分離した本人用Hermesをどこで動かし、Cloudflareに何を任せるか、その構成で画面上の約束を守れるか**です。成果物はレビュー報告です。コード変更、デプロイ、有料リソースの作成はスコープ外です。

## 製品の狙い

一般社員が職種を問わず、普段の言葉で調査・集計・文書作成・業務手続きを頼める製品を目指しています。社員はHermesの設定やツール名を知らなくても、使った資料、回答の根拠、次に実行される操作を確認できる必要があります。本人の会話・記憶・個人スキルを分離し、全社知識と公開されたチーム手順を再利用できることが重要です。管理者も自分の仕事を持ち、管理操作は専用メニューから行います。

## 設計上の判断を求める点

1. **Hermesの配置と永続化。** Cloudflare Containersでユーザー別に起動する案と、別基盤のユーザー別コンテナをCloudflareから呼ぶ案を、同じ条件で比較してください。コールドスタート、休止・更新時の復元、SQLite・メモリ・スキルの永続化、同一社員の同時依頼、資格情報の分離が判断軸です。Hermesを維持する前提で推奨案を一つ選び、選択が逆転する条件を示してください。
2. **認可とRAG。** 認証された社員から検索対象を決め、全社規程・社内用語・部門限定資料の該当箇所だけがモデルに届くかを追ってください。部門異動、旧版規程、索引更新の遅れ、キャッシュ、過去の成果物・出典リンク・共有先まで含め、どの時点で権限と版を再確認するかを評価してください。個人メモリの削除やスキルのチーム公開で、元資料や他人の履歴が混入しないかも対象です。
3. **二重実行と復旧。** Hermesが受け付けた直後に通信が切れ、Hubには実行IDが残らないケースを一つ追ってください。再起動・イベント再配信・承認ボタンの連打が重なっても、同じ会議メモや窓口登録を再送せず、後続の週報を進められるでしょうか。照合に使う識別子、状態の正本、費用の予約・精算、手動判断に戻す条件まで確認してください。
4. **運用と費用。** 個人情報を含む本文・ログの保存場所、外部モデルへの送信先、削除・バックアップ復元、監査権限、障害時の切り分けを確認してください。運用費と待ち時間を左右する少数の変数を挙げ、規模・予算が不明なら仮定を明示してください。Cloudflareの提供状況、制限、課金に依存する結論には現行の公式資料と確認日を付けてください。調査の入口は[コンテナのライフサイクル](https://developers.cloudflare.com/containers/concepts/architecture/)、[Queuesの配信保証](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)、[AI Search](https://developers.cloudflare.com/ai-search/)です。

## モックアップで実際に追ってほしい操作

| 操作 | 見てほしい点 |
|---|---|
| 営業企画部の佐藤が、ホームで資料を選ばず「出張を取り消すときの手続きと、証憑の意味を教えて」と質問し、両方の出典を開く | 条項と定義を元の仕事で判別できるか。根拠が見つからない場合や、ある主張だけ裏付けがない場合に、それを社員が読み取れるか |
| 佐藤と購買部の加藤が「POの意味と、発注前に確認する条件を教えて」と質問する。次に青木が加藤を別部門へ異動させ、加藤が元の仕事を開く | 同じ質問への結果の違い、失効後の本文・出典の表示、非公開資料の存在を推測させる表示がないか |
| 管理者の青木が「2社の見積比較」の公開先と推奨先を設定し、社員別プレビューを見る。一般社員・閲覧専用管理者の森でも開く | 「利用できる」と「おすすめ」の違い、青木の個人作業と管理操作の区別、森が監査できる範囲と変更できる範囲が伝わるか |
| 成果物から窓口登録案を作り、担当者が差し戻す。依頼者が同じ受付を修正し、承認後に元の仕事から開く | 下書き・承認待ち・登録済みの違いと、誰が何を送るのかを実行前に判断できるか。狭い画面やキーボード操作で詰まる箇所はあるか |

静的HTMLの社員切り替えはデモです。画面の使いやすさは操作して評価し、サーバー側の認可、実Hermesの推論、実検索品質、Cloudflare上の耐障害性は、それぞれに必要な証拠を挙げてください。

## 期待する回答

- **冒頭に採否判断。** 「採用可能」「条件付きで採用」「設計変更が必要」から一つ選び、推奨構成と最大の未解決点を短く述べてください。
- **優先指摘は最大8件。** 各件に重大度、根拠となるファイル・行または画面操作、発生条件、社員・運用への影響、最小の修正案、修正を確認するテストを付けてください。画面の問題と基盤の問題を対応づけてください。
- **構成図を一枚。** 社員別Hermes、認証・認可、検索、モデル、永続化、監査の境界を示し、規程への質問が回答・出典表示に至る経路を描いてください。
- **最後に次の一手を一件。** 最も不確実性を減らせるPoCを選び、実行条件、観測値、合格基準、失敗した場合に変更する設計判断を書いてください。設計の判断に利用者数・同時実行数・データ所在などの情報が必要なら、確認事項は優先順に最大3問に絞ってください。
